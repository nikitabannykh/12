# Архитектура «Самохода»

Одно приложение Next.js 16 (App Router): страницы, API и робот в одном репозитории. База — Postgres (Neon на проде, встроенная PGlite локально). Очередей и отдельных воркеров нет: робот — обычная функция, которую вызывает расписание.

```
Браузер владельца ──► /app/* (Server Components) ──► src/lib/engine/*  ──► src/lib/platforms/*  ──► Директ / Метрика / VK / демо
                     /api/*  (Route Handlers)   └─► src/lib/ai/*       ──► YandexGPT / YandexART
Сайт владельца ── /t.js ──► /api/t                  └─► src/lib/db (Drizzle) ──► Postgres
Страница записи /p/<key> ──► /api/lead ──► Telegram-уведомление (src/lib/notify.ts)
Vercel Cron / GitHub Actions ──► /api/cron/run ──► engine/run.ts (sync + optimizer)
```

## Модули

| Путь | Что делает |
|---|---|
| `src/app/app/*` | Кабинет владельца: главное, реклама, статистика, история, настройки, анкета (`start`), мастер запуска (`launch`) |
| `src/app/p/[key]` | Страница записи для бизнеса без сайта |
| `src/app/t.js` | Скрипт-трекер для сайта владельца: формы, клики по телефону и мессенджерам → цели Метрики + `/api/t` |

## Модель данных

Схема — `src/lib/db/schema.ts` (Drizzle), SQL — `src/lib/db/migrate.ts`. Таблицы создаются автоматически при первом подключении (`CREATE TABLE IF NOT EXISTS`). Проверка, что ORM и SQL совпадают: `npm run check:schema`.

| Таблица | Содержимое |
|---|---|
| `users` | Пользователи (почта, Google, ссылка из письма или демо): `password_hash` (scrypt, `null` — пароль не задан), `email_verified_at`, `session_version` (входит в cookie сессии; растёт при смене/сбросе пароля) |
| `businesses` | Анкета бизнеса, месячный бюджет, статус (`draft / launching / active / paused`), счётчик и цели Метрики, регионы, план запуска, публичный ключ для трекера и страницы записи |
| `ad_accounts` | Подключённые кабинеты: площадка, логин, **зашифрованные** access/refresh-токены (AES-256-GCM), срок действия, статус |
| `campaigns` | Кампании: канал (`search / network / vk / retarget_yandex / retarget_vk`, справочник — `src/lib/channels.ts`), внешний ID, статус (`creating / active / paused / archived / error`), недельный лимит, стратегия (`clicks / conversions`), минус-слова, `meta` (предел ставки, `pausedByGuard`, `pausedBy`, `guardCutFrom/To`; у ретаргетинга — `audience` {state `collecting / on / off`, need, size, since, note} и `audienceId`) |
| `ad_groups` | Группы (аудитории): ключевые фразы, таргетинг, статус |
| `ads` | Объявления: подход (`angle`), тексты, картинка, статус модерации, связь с тестом и «родителем» |
| `images` | Фото владельца, сгенерированные и собранные картинки (`bytea`), ссылки на загруженные на площадки копии |
| `stats_daily` | Статистика по дням: объявление × день (`ad_id = ""` — итог кампании), показы, клики, расход, конверсии, взвешенные объём трафика и позиция |
| `experiments` | A/B-тесты: тип (`ad / audience`), гипотеза, контроль и вариант, итог |
| `changes` | История: кто (`robot / owner`), что, почему, детали, **обратные операции** (`undo`), отметка отмены |
| `leads` | Обращения: форма, телефон, мессенджер; источник и объявление по utm; статус владельца (`booked / no_answer / spam`, `status_at`); ClientID Метрики и `yclid` для офлайн-конверсий |
| `client_marks` | Сколько обратившихся записались — недельная отметка владельца |
| `jobs` | Блокировки (`lock` — робот, `launch` — запуск) и время последнего запуска периодических задач (минус-слова, перенос бюджета, место в выдаче, `budget_month`) |
| `kv` | Служебные значения: демо-часы, состояние Telegram-бота, баланс кабинетов (`balance:<кабинет>`) и время последнего предупреждения, загруженные офлайн-конверсии (`mo:<бизнес>`), использованные ссылки из писем (`auth:used:<sha256 nonce>`, `value.exp` — срок ссылки) |
| `rate_limits` | Счётчики ограничения частоты для открытых эндпоинтов (IP хранится только в виде отпечатка) |
| `notify_settings` | Привязанный Telegram-чат владельца и настройки сводки |

## Площадки

Интерфейс `PlatformClient` (`src/lib/platforms/types.ts`): `launchCampaign`, `addAd`, `setCampaignActive`, `setAdsActive`, `setBudget`, `setNegativeKeywords`, `updateAdText`, `getAdStates`, `getStats`, необязательные `getAuction` и `getSearchQueries`. `clientFor(account)` выбирает реализацию, расшифровывает токены и при необходимости обновляет их.

| Клиент | API | Особенности |
|---|---|---|
| `YandexDirect` (`yandex.ts`) | Direct API `v501` (ЕПК — `UnifiedCampaign`), Reports API `v5` | Отдельные кампании для поиска и РСЯ; стратегии `WB_MAXIMUM_CLICKS` → `WB_MAXIMUM_CONVERSION_RATE` с `WeeklySpendLimit` и `BidCeiling`; картинки, уточнения, быстрые ссылки, `ErirAdDescription`; аукцион через `keywordbids`; поисковые запросы из отчёта. Песочница — `YANDEX_DIRECT_SANDBOX=true`. Токен Яндекса живёт год, обновляется за 14 дней до окончания |
| Метрика (`metrica.ts`) | Management API | Счётчик и цели «JavaScript-событие»: `pz_lead`, `pz_form`, `pz_phone`, `pz_messenger`. Директ оптимизирует по `pz_lead` |
| `VkAds` (`vk.ts`) | VK Ads API v2 | `ad_plans` → группы → `banners`; формат по «пакету» (автоподбор или `VK_ADS_PACKAGE_ID`); бюджет дневной; токен живёт сутки и обновляется по refresh-токену |
| `DemoPlatform` (`demo.ts`) | — | Моделирует показы, клики, обращения, модерацию и аукцион; время — «демо-часы», которые можно промотать |

## Каналы и типы кампаний

Справочник — `src/lib/channels.ts` (общий для сервера и интерфейса). **Канал** (`campaigns.channel`) — отдельная кампания на площадке со своим недельным лимитом; **тип** — как её видит владелец; **формат** — какие объявления и лимиты текста.

| Канал | Площадка | Тип | Как устроен | Минимум, ₽/нед | Доля бюджета |
|---|---|---|---|---|---|
| `search` | Директ | Поиск | ЕПК, `Network: SERVING_OFF`; с организацией — места показа `Maps`, `SearchOrganizationList` | 370 | 50 |
| `network` | Директ | Сети | ЕПК, `Search: SERVING_OFF`, автотаргетинг | 370 | 25 |
| `vk` | VK Реклама | Соцсети | `ad_plans`, радиус вокруг адреса, возраст | 854 | 25 |
| `retarget_yandex` | Директ | Ретаргетинг | ЕПК в сетях; группа без фраз с `audiencetargets.add` → условие `retargetinglists.add`: цель Метрики «посетил сайт» (url, «содержит» домен; создаётся `ensureVisitGoal`) ANY + цель «обращение» NONE, 30 дней | 370 | 7 (вес) |
| `retarget_vk` | VK Реклама | Ретаргетинг | группа с `targetings.segments` → сегмент `remarketing/segments.json`: пиксель (`remarketing_counter`, `goal_id: "uss"`) positive + событие `lead` negative, 30 дней | 854 | 7 (вес) |

Веса делятся на сумму включённых каналов: при всех пяти ретаргетинг получает ≈ 6 % на площадку (10–12 % вместе). Порядок важности (кого отключать при нехватке бюджета): поиск → РСЯ → VK → ретаргетинг Яндекса → ретаргетинг VK. При 30 000 ₽/мес ретаргетинг VK не помещается в минимум VK — его можно добавить позже из «Рекламы».

**Карты** — не канал: это места показа поисковой ЕПК при привязанной организации (`business.orgId`, `yandex.ts → linkableBusiness`). В интерфейсе — карточка типа «Карты» без своего бюджета («подключено» / «привяжите организацию»).

**Ретаргетинг включается сам.** Кампания создаётся при запуске выключенной (Директ — объявления-черновики, VK — план `blocked`, демо — `pending`) и сохраняется со статусом `paused`, `meta.audience.state = "collecting"`. Пока копит аудиторию, она не тратит, в раскладке бюджета не участвует (`activateLaunch` делит бюджет только между работающими каналами) и не считается «паузой» ни для защиты бюджета, ни для кнопки «Включить всё». Шаг робота «Ретаргетинг» (`engine/retarget.ts → retargetStep`, сразу после защиты бюджета) оценивает аудиторию — переходы из рекламы той же площадки за 30 дней с момента запуска × 0,7 (доля уникальных людей) − обращения; для настоящего Директа ещё посетители по Метрике (`/stat/v1/data`, `ym:s:users`) − обращения, берётся большее. Площадки размер аудитории через API не отдают. Когда набралось `RETARGET_MIN_AUDIENCE = 100`, робот пересчитывает лимиты (`planLimits` по работающим кампаниям + ретаргетинг с долей из `allocate`, сумма = min(текущая сумма, безопасный остаток месяца)), одним изменением в истории уменьшает лимиты остальных и включает кампанию (отменяемо), затем `activateCampaign` на площадке (модерация черновиков). Не хватает бюджета на минимум — не включает и пишет в `meta.audience.note`, сколько нужно. Владелец может отключить автовключение (тумблер на карточке → `state: "off"`). Ретаргетинг не участвует в переносах бюджета между каналами (маленькая аудитория больше не потратит).

**Демо** считает аудиторию так же — по смоделированной статистике, поэтому она растёт с каждым днём. Ретаргетинг в демо не «стартует задним числом» (без 12 дней истории), начинает показы в день включения, клик дешевле, CTR и конверсия выше, но кликов в день мало (6–9).

**Ссылки в кабинет** (`cabinetUrl`): Директ — `https://direct.yandex.ru/dna/grid/campaigns?ulogin=<логин>&campaigns-ids=<ID>`, VK — список кампаний `https://ads.vk.com/hq/dashboard/ad_plans?ad_plan_id=<ID>`. Документированного формата у площадок нет — проверить на живом кабинете; номер кампании показан рядом.

**Навигация.** «Реклама» (`/app/ads?p=yandex|vk&t=search|network|feed|retarget|maps`): липкие фильтры «Площадка» и «Тип» со счётчиками (ссылками — состояние в адресе), обзор «Кампании» (тип, назначение, статус, расход, обращения, цена обращения, клиент) со ссылками-якорями `#c-<id>` / `#maps` на карточки. С фильтром общие блоки (лучшие идеи, тесты, фото) скрыты. В боковом меню под «Рекламой» — «Яндекс» и «VK» со счётчиками; на «Главном» карточка «Каналы» ведёт на отфильтрованную «Рекламу».

## Запуск рекламы

1. **Анкета** (`/app/start`, `POST /api/business`) — можно заполнить автоматически по ссылкам на сайт, карты и онлайн-запись (`/api/business/import`, см. «Автозаполнение по ссылке»).
2. **Кабинеты** — OAuth Яндекса и/или VK, либо демо-кабинет.
3. **Бюджет** — `allocate()` делит месячный бюджет на недельные лимиты каналов (веса: поиск 0,5, РСЯ 0,25, VK 0,25, ретаргетинг 0,07 на площадку) с учётом минимумов площадок; если денег не хватает, отбрасывает наименее приоритетный канал (первым — ретаргетинг).
4. **Тексты** (`/api/launch/copy`) — YandexGPT или шаблоны ниши: группы, ключевые фразы, минус-слова, по 3 объявления с разными подходами. Ретаргетинг — одна группа «Были на сайте, но не записались» из объявлений основного канала площадки (РСЯ / VK), без фраз и минус-слов.
5. **Картинки** (`/api/launch/images`) — фото владельца или YandexART + макеты.
6. **Запуск** (`/api/launch/publish`, `publishStep`) — по одному каналу за вызов, мастер повторяет вызов, пока все каналы не готовы. Запуск держит блокировку (`jobs.kind = 'launch'`), повторный клик получает 409. Для канала: регионы, Метрика, затем запись кампании в БД со статусом `creating` **до** вызова площадки и внешний ID сразу после её создания. Если функцию прервали, следующий вызов удаляет недосозданную кампанию на площадке и создаёт заново; каналы с готовыми кампаниями пропускаются. В конце — событие `launch` в истории.

## Робот

### Когда запускается

| Триггер | Маршрут | Частота |
|---|---|---|
| Vercel Cron | `GET /api/cron/run` (заголовок `Authorization: Bearer CRON_SECRET`) | Раз в сутки (`vercel.json`; на Hobby чаще нельзя, время ±59 мин) |
| GitHub Actions | `GET /api/cron/run` (заголовок `Authorization: Bearer CRON_SECRET`, `.github/workflows/optimizer.yml`) | Каждые 2 часа (`17 */2 * * *`), с задержками GitHub |
| Владелец | `POST /api/run` («Проверить сейчас») | По кнопке |
| Демо | `POST /api/demo/advance` | Перемотка на 1–14 дней, проход робота за каждый день |
| После запуска | внутри `publish` | Один раз |

`runAll()` обходит активные бизнесы — сначала тех, кого дольше не проверяли, — пока не истечёт дедлайн (~45 с), затем cron рассылает Telegram-сводки. `runBusiness()` берёт атомарную блокировку на бизнес (`INSERT … ON CONFLICT … WHERE locked_until < now()` в `jobs`, 4 минуты), вызывает `syncBusiness()` (статистика за 30 дней, статусы модерации, обращения трекера по московскому дню) и, если бизнес активен, `optimizeBusiness()`.

В демо у каждого демо-кабинета свои часы (`kv: demo:clock:<accountId>`), и история пишется по ним же.

### Шаги одного прохода (`optimizeBusiness`)

Шаги выполняются по порядку; ошибка одного шага пишется в лог и не останавливает остальные.

| Шаг | Что делает | Как часто |
|---|---|---|
| Бюджет месяца | См. ниже «Защита бюджета» | Каждый проход |
| Ретаргетинг | Обновляет размер аудитории; при ≥ 100 человек включает кампанию и делит бюджет заново (см. «Каналы и типы кампаний») | Каждый проход |
| Модерация | Переписывает отклонённые объявления с учётом причины отказа | Каждый проход |
| Итоги тестов | При уверенности ≥ 90 % отключает проигравший вариант; через 21 день без победителя оставляет лучший | Каждый проход |
| Перенос идей | Подход, победивший в одной группе, тестирует в соседних | Каждый проход |
| Место в выдаче | Поиск: по аукциону выставляет или снимает предел ставки | Раз в ~6,5 дня |
| Объявления | Отключает явно слабые (≥ 95 % и ≥ 1,4×) и «сливающие», для пограничных запускает тест, держит в группе ≥ 2 рабочих | Каждый проход |
| Картинки | Тесты макетов картинок | Каждый проход |
| Аудитории | Отключает аудиторию, где обращение вдвое дороже лучшей | Каждый проход |
| Минус-слова | Разбирает поисковые запросы (правила ниши + YandexGPT), добавляет нецелевые | Раз в ~3 дня |
| Стратегия | При ≥ 10 обращений в неделю переключает Директ с кликов на заявки | Каждый проход |
| Бюджет каналов | Переносит четверть бюджета из самого дорогого канала в самый дешёвый | Раз в ~6,5 дня |

Ограничения: не больше 4 новых объявлений за проход; решения только при достаточных показах (поиск — 150, РСЯ и VK — 1 500, ретаргетинг — 600); объекты, которые владелец менял за последние 14 дней (`Ctx.protected`), робот не трогает.

### Обучение площадок
`learningLeft()` считает, сколько дней кампания ещё учится: после запуска — VK 7 дней, Директ 14; после смены стратегии — 7 / 14; после изменения лимита или предела ставки — 7. Поправки защиты бюджета (`details.guard`) обучение не продлевают. Пока кампания учится, шаги «Бюджет каналов» и «Место в выдаче» её пропускают (`skipLearning`); защита бюджета действует всегда.

### Защита бюджета
Чистая математика — `engine/budget-plan.ts`, состояние месяца — `engine/budget-guard.ts`, шаг — `budgetGuard()` в `optimizer.ts`.

1. `budgetState()` — расход с 1-го числа и остаток; в демо сегодняшний неполный день не считается.
2. Общий недельный лимит = минимум из «бюджет на все дни месяца» и «остаток / оставшиеся дни × 7».
3. `planLimits()` раскладывает его по кампаниям пропорционально желаемым лимитам с учётом минимумов площадок (Директ 300 ₽/нед, VK 700 ₽/нед); если минимумы не помещаются — отключает наименее важный канал (порядок важности: поиск → РСЯ → VK).
4. Если остатка меньше, чем реклама потратит до следующей проверки (`reserveFor`: 2 дня × 1,3 на площадках, 1 день × 1 в демо), — пауза всего до 1-го числа (`meta.pausedByGuard`).
5. В середине месяца лимиты только снижаются; в новом месяце (job `budget_month`) возвращаются к прежним (`meta.guardCutFrom`) и включаются кампании, остановленные из-за бюджета. Паузу владельца (`meta.pausedBy = 'owner'`) робот не снимает.
6. Владелец меняет бюджет (`applyMonthlyBudget`) — лимиты пересчитываются в обе стороны, остановленное из-за бюджета включается, если денег хватает. Сервер не принимает бюджет ниже `minMonthlyFor()`.

## Как работает отмена

- Любое изменение рекламы — это список операций `UndoOp`: `campaignStatus`, `adStatus`, `groupStatus`, `campaignBudget`, `campaignStrategy`, `bidCeiling`, `addNegatives` / `removeNegatives`, `adText`, `monthlyBudget`.
- `applyOp(op)` выполняет операцию на площадке и в БД и **возвращает обратную**, записанную по состоянию до изменения.
- `act(change, ops)` применяет набор через `applyOps()`: если одна операция падает, уже применённые откатываются. Обратные операции сохраняются в `changes.undo`.
- `revertChange(id)` применяет `undo`, ставит `reverted_at` и пишет новое изменение `kind = revert` (поле `revert_of`) со своими обратными операциями — поэтому отмену тоже можно отменить. Цепочка «отмена отмены…» сводится к исходному изменению: чётная глубина — отменяем, нечётная — возвращаем.
- Действия, которые нельзя выразить операциями (например, создание объявления), откатываются паузой: `undo = [adStatus → paused]`. Побочные эффекты восстанавливаются отдельно: отмена `test_start` закрывает тест и возвращает объявления в обычную оптимизацию, отмена замены отклонённого объявления возвращает старое.
- Обратные операции хранят **абсолютные** прежние значения, поэтому перед отменой есть две проверки:
  - `assertNoNewerChanges` — если тот же объект (ключи вида `c:<id>:weekly`, `a:<id>:status`) после этого менялся ещё раз и то изменение действует, отмена отклоняется с ответом 409 и названием более позднего изменения;
  - `assertFitsBudget` — отмена не может включить рекламу или поднять лимиты сверх месячного бюджета.
- `applyOp(campaignStatus)` запоминает, кто поставил паузу (`meta.pausedBy`), и сбрасывает пометку «пауза из-за бюджета» — так робот отличает паузу владельца от своей.

## Безопасность

- Сессия — подписанная HMAC cookie (`httpOnly`, `SameSite=Lax`). Секрет — `APP_SECRET`; если его нет, он выводится из строки подключения к базе (смена пароля базы тогда сбрасывает сессии и делает нечитаемыми сохранённые токены кабинетов).
- Токены кабинетов хранятся зашифрованными (AES-256-GCM). OAuth `state` проверяется во всех колбэках.
- **Вход по почте.** Почта приводится к виду `trim().toLowerCase()`, пароль — от 8 до 200 символов. Хеш — `scrypt` (N=16384, r=8, p=1, 64 байта) с отдельной солью у каждого пользователя, формат `scrypt$N$r$p$соль$хеш`; сравнение — `timingSafeEqual`. Для несуществующей почты scrypt всё равно считается, ответ одинаковый: «Неверная почта или пароль». Лимиты: 10 попыток входа (и регистраций) за 15 минут на IP и на почту; восстановление — 10 за 15 минут на IP и 5 в час на почту; смена пароля — 10 за 15 минут на пользователя. Все формы — через `sameOrigin` (`publicRoute` в `api.ts` для форм без входа, `route()` для смены пароля).
- Если у почты нет пароля (вошли через Google или по ссылке), вход по паролю отвечает «Войдите через Google или восстановите пароль, чтобы задать его» — это сознательный компромисс в пользу понятности; восстановление пароля, наоборот, ничего не раскрывает: «Если такой адрес есть, мы отправили письмо», письмо уходит после ответа (`after()`), так что и по времени ответа не понять.
- **Сессии.** Cookie `pz_session` = HMAC-подпись `{uid, sv, exp}`, где `sv` = `users.session_version`. `getUser` сверяет `sv` с базой (старые cookie без `sv` считаются версией 0). Смена или сброс пароля увеличивает версию: все прочие устройства выходят, текущему выдаётся новая cookie.
- **Ссылки из писем** — подписанные HMAC токены: сброс пароля `{p:"reset", u, sv, ph, n, exp: 1 час}` (`ph` — отпечаток текущего хеша пароля, так что ссылка гаснет при любой смене пароля), вход по ссылке `{p:"magic", e, sv, n, exp: 15 минут}`, подтверждение почты `{p:"verify", u, e, exp: 7 дней}`. Сброс и вход одноразовые: при использовании `INSERT … ON CONFLICT DO NOTHING` в `kv` с ключом `auth:used:<sha256(n)>`. Вход по ссылке — только POST с кнопки на странице `/login/link/…`: почтовые сканеры открывают ссылки сами и иначе тратили бы их. На страницах со ссылкой стоит `<meta name="referrer" content="no-referrer">` — токен из адреса не уходит на чужие сайты.
- **Захват аккаунта до подтверждения почты.** Регистрация по паролю не требует подтверждения почты, поэтому кто-то может зарегистрироваться на чужой адрес. Когда настоящий владелец почты входит через Google или по ссылке из письма (то есть доказывает владение адресом), а почта ещё не подтверждена, заданный ранее пароль стирается и все сессии сбрасываются. Без SMTP почта не подтверждается, и пароль при первом входе через Google тоже сотрётся — его можно задать заново в «Настройках → Аккаунт».
- **Почта** (`mail.ts`): `SMTP_URL` (nodemailer, например `smtps://login:app-password@smtp.yandex.ru:465`), `MAIL_FROM`. Без `SMTP_URL` регистрация работает без подтверждения, «Войти по ссылке» скрыт, восстановление отвечает «Восстановление по почте пока не настроено — напишите в поддержку», а при локальном запуске ссылка сброса печатается в консоль (`[mail:dev] …`). `SMTP_URL=json://` — тестовый режим: письма печатаются в лог (`[mail:json] {…}`) вместо отправки. Ошибка SMTP не ломает регистрацию и не раскрывается в ответе — только в логе сервера.
- Все маршруты изменения сверяют владельца бизнеса. Картинки отдаются по неугадываемому ID.
- `/api/lead` и `/api/t` открыты (ключ страницы публичный) и защищены лимитом частоты через `rate_limits`.
  - IP для лимитов берётся только из заголовков, которые не подделать (`clientIp` в `ratelimit.ts`): на Vercel — `x-vercel-forwarded-for` / `x-real-ip`; за своим прокси — заголовок из `TRUSTED_IP_HEADER`. Без них `x-forwarded-for` присылает сам клиент (Next.js его не перезаписывает), поэтому IP считается неизвестным и лимиты по IP не применяются — остаются одноразовый токен формы и пометка «похоже на спам». Сам IP не хранится — только отпечаток.
  - С одного IP — 5 заявок за 10 минут и 20 в сутки. Общего лимита на бизнес нет, чтобы спамер не мог закрыть приём настоящих заявок: после 20 заявок за час следующие сохраняются с `kind = 'suspect'`, без привязки к объявлению (не влияют на решения робота), владельцу приходит одно предупреждение вместо сообщения о каждой. В «Статистике» они помечены «похоже на спам».
  - Форма получает одноразовый подписанный токен (время открытия + nonce, срок 2 часа). Заявка быстрее 3 секунд после открытия отклоняется, повтор того же токена — 409. Если страница открыта дольше 2 часов, форма сама берёт новый токен (`GET /api/lead?key=`) и отправляет заявку, не теряя введённое.
  - Телефон: российский номер приводится к `7XXXXXXXXXX` (ровно 11 цифр, код 3/4/8/9 или Казахстан 6/7), иностранный — только с `+`; номера из одинаковых цифр и «лесенки» отклоняются.
- Привязка Telegram: код в ссылке `t.me/<бот>?start=<код>` случайный, одноразовый и живёт 15 минут (`kv: tg:link:<код>`). Бот спрашивает «Подключить уведомления для «…»?» и привязывает чат только после кнопки «Подключить» (`callback_query`), код при этом гаснет. Если бот заблокировали, удалили из группы или чат удалён, уведомления отключаются, а причина сохраняется (`kv: tg:unlinked:<businessId>`) и показывается в настройках.
- `/api/cron/run` принимает `CRON_SECRET` только в заголовке `Authorization: Bearer <CRON_SECRET>` (параметр `?key=` больше не поддерживается: ключ в адресе попадает в логи). Если `CRON_SECRET` не задан, на Vercel пропускается запрос с `User-Agent: vercel-cron…`, но не чаще раза в 30 минут — заголовок легко подделать, поэтому `CRON_SECRET` нужно задать.
- После прохода робота cron рассылает утренние сводки в Telegram и чистит просроченные счётчики лимитов, а также контакты в заявках старше 3 лет.

## Заявки, офлайн-конверсии и баланс

**Статус заявки.** Владелец отмечает заявку кнопкой в Telegram (под сообщением о заявке) или в «Статистике». Вебхук проверяет, что нажали в чате, привязанном к бизнесу этой заявки (`notify_settings.telegram_chat_id`), и меняет клавиатуру сообщения (✓ у выбранного статуса). Общая функция — `setLeadStatus` в `ops.ts`.

**Клиенты в отчёте** (`report.ts`), по дням периода:
1. неделя с отметкой «сколько клиентов» → обращения × (клиенты недели / обращения недели), как раньше;
2. иначе: заявки «Записался» — клиенты, «Не дозвонились» — нет, остальные обращения (в том числе конверсии площадки без нашей заявки) × доля из анкеты → `clientsEstimated`;
3. «Спам» исключён из обращений везде (`report.ts`, `sync.ts`, сводка).

**Офлайн-конверсии** (`syncOfflineConversions`, каждый проход робота): заявки «Записался» за 21 день с ClientID или `yclid`, ещё не загруженные (`kv mo:<бизнес>`). Цель `pz_booked` (JavaScript-событие, условие «совпадает») создаётся при первой загрузке и сохраняется в `businesses.goal_ids.booked`. CSV: строки с ClientID — `ClientId,Target,DateTime`, только с `yclid` — отдельным файлом `Yclid,Target,DateTime`; `DateTime` — unix-время отметки (не позже «сейчас»). Нужен кабинет Яндекса с правом `metrika:write`.

**Баланс** (`checkBalances`, каждый проход робота после синхронизации): для кабинетов с активными/остановленными кампаниями бизнеса. Директ — `POST /live/v4/json/ {method: "AccountManagement", param: {Action: "Get"}, token}` → сумма `Accounts[].Amount` (пустой список — общий счёт не включён, остаток неизвестен). VK — `account.balance` из `v2/user.json` [проверить поле]. Дни = остаток ÷ (расход за 7 дней / 7); остаток < 1 ₽ при работающих кампаниях — «кончились». При ≤ 3 днях — сообщение в Telegram не чаще раза в 20 часов (сразу, если стало хуже) и баннер на «Главном». Реальные площадки опрашиваются не чаще раза в 3 часа.

**Здоровье рекламы** (`health.ts`): пункты с весами — кабинеты (20), баланс (20), счётчик и цель (15), отметки заявок (10), организация в Картах (10), модерация (10), бюджет (10), часы работы (5), свои фото (5). Балл = вес выполненных / вес применимых × 100; пункт, который нельзя проверить (нет баланса, нет заявок), не учитывается.
